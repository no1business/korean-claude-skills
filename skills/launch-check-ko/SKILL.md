# 출시 전 점검 (한국판)

바이브코딩으로 만든 서비스를 출시하기 전에 세 가지를 점검한다. 결과는 "고칠 곳 목록"이다.

1. **비밀 키 노출**: 결제 키, 관리자 키, API 키가 코드에 그대로 있거나 브라우저에 보이는 이름(NEXT_PUBLIC_ 등)으로 쓰이는지
2. **개인정보처리방침**: 앱이 실제로 받는 정보·연결한 외부 서비스와 처리방침에 적힌 내용이 맞는지, 필수 항목이 빠지지 않았는지
3. **다크패턴 의심 화면**: 전자상거래법 다크패턴 6가지 기준(취소·탈퇴 방해, 숨은 갱신, 특정옵션 사전선택, 순차공개 가격, 잘못된 계층구조, 반복간섭)

답은 항상 한국어 존댓말로, 짧게 한다.

## 1단계: 코드 받기

- claude.ai: 사용자가 프로젝트 폴더를 zip으로 올린다. (node_modules는 빼고 압축하라고 안내)
- 클로드 코드: 지금 폴더를 그대로 점검한다.
- 코드가 없고 화면만 있으면 스크린샷을 받아 3단계 기준으로 직접 보고 판단한다.

## 2단계: 자동 점검 돌리기

```
python scripts/scan.py <폴더 또는 zip> 출시전_점검결과.md
```

스크립트가 키 패턴·입력 칸·결제/분석 SDK·처리방침 문구·구독/해지/체험/체크박스 코드를 훑어서 후보를 뽑는다.

## 3단계: 후보를 직접 확인하기 (중요)

스크립트 결과는 후보다. 표시된 파일과 줄을 **직접 열어서** 확인한다.

- 테스트 키(test_), 예시 값, 주석은 빼거나 "확인 권장"으로 낮춘다.
- 스크립트가 못 찾는 것도 본다:
  - 가격 화면과 마지막 결제 화면의 금액이 다른지 (순차공개 가격)
  - "해지" 버튼만 흐리고 작게, "유지" 버튼만 크게 만들었는지 (잘못된 계층구조)
  - 구독료 인상·유료 전환 때 다시 동의를 받는지 (숨은 갱신)
  - 회원 탈퇴 경로가 있는지
  - 서버(API 라우트)에서 로그인 확인 없이 다른 사람 데이터를 주는 곳이 있는지
- 클로드 코드를 쓰는 사용자에게는 `/security-review` 명령도 함께 돌려 보라고 안내한다.

## 4단계: 결과 주기

- `출시전_점검결과.md` 파일을 준다. 세 칸: 비밀 키 / 개인정보처리방침 / 다크패턴.
- 대화창에는 한 줄 요약 + "고칠 것" 상위 5개만 쓴다. 예: "비밀 키 2건 · 처리방침 5건 · 다크패턴 2건, 먼저 고칠 것: …"
- 사용자가 "고쳐줘"라고 하면 해당 파일을 고친다. 키는 환경변수로 옮기고, **이미 깃허브·배포에 올라갔던 키는 반드시 새로 발급**하라고 안내한다.
- 처리방침 수정이 필요하면 빠진 항목만 초안으로 써 준다(수집 항목, 보유 기간, 위탁 업체, 보호책임자 등). 개인정보보호위원회 "개인정보 처리방침 작성지침"을 참고하라고 덧붙인다.

## 지켜야 할 것

- 찾은 키 값은 앞 6자리만 보이고 나머지는 가린다. 전체 키를 대화창에 다시 쓰지 않는다.
- "불법입니다", "과태료 ○○원" 같은 단정은 하지 않는다. "~에 해당할 수 있어요, 출시 전에 확인하세요"까지만 말한다.
- 최종 법적 판단은 변호사·개인정보보호 전문가에게 확인하라고 덧붙인다.
